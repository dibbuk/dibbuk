# Project delivery artifacts — illustrative templates

[Русская версия](delivery-artifacts.ru.md) · [Back to profile](../README.md)

This page contains lightweight, sanitized examples of the types of artifacts used to structure and control complex technology delivery. They are **illustrative templates**, not copies of confidential project documents or claims that every item was used in exactly this form on a particular project.

## 1. Project one-page brief

| Field | Content |
|---|---|
| Business outcome | What business or operational result must change |
| Problem / opportunity | Current state, pain point, risk or opportunity |
| Scope | Included capabilities, processes, sites and interfaces |
| Out of scope | Explicit exclusions and boundaries |
| Success measures | Measurable acceptance and outcome criteria |
| Sponsor / owner | Business sponsor and accountable process owner |
| Delivery model | Waterfall, Agile or hybrid; rationale |
| Budget / timeline | Approved baseline and key milestones |
| Key dependencies | Systems, vendors, sites, decisions and resources |
| Top risks | Main threats, owners and mitigation actions |

## 2. WBS and milestone outline

| Workstream | Typical deliverables | Exit evidence |
|---|---|---|
| Initiation | Business case, charter, stakeholder map | Sponsor approval |
| Discovery | AS-IS / TO-BE, requirements, process scope | Requirements baseline |
| Solution | Architecture decisions, integration design | Design approval |
| Procurement | RFI / RFP, evaluation, SOW, contract | Vendor and contract approval |
| Delivery | Configuration / development, integrations | Demonstrable increments |
| Verification | Test strategy, SIT, UAT, defect log | Test and business acceptance |
| Deployment | Cutover plan, go/no-go, rollback readiness | Go-live decision |
| Transition | Training, documentation, support model, SLA | Operational handover |
| Closure | Acceptance, financial closure, lessons learned | Sponsor sign-off |

## 3. RAID log

| ID | Type | Description | Impact | Owner | Response / next action | Due date | Status |
|---|---|---|---|---|---|---|---|
| R-01 | Risk | Example: interface specification is not approved | Schedule / rework | Solution owner | Agree interface contract and review date | YYYY-MM-DD | Open |
| A-01 | Assumption | Example: source data will be available for migration rehearsal | Test readiness | Business owner | Validate sample and access | YYYY-MM-DD | To validate |
| I-01 | Issue | Example: test environment is not ready | SIT start | Technical lead | Escalate dependency and recovery plan | YYYY-MM-DD | Open |
| D-01 | Dependency | Example: vendor API is required before end-to-end test | Critical path | Vendor manager | Confirm delivery date and fallback | YYYY-MM-DD | Open |

## 5. Change request

- Change ID and requester
- Business rationale
- Description of requested change
- Impact on scope, requirements, architecture and interfaces
- Impact on schedule, budget, resources, risks and benefits
- Options considered
- Recommendation and decision owner
- Approval, rejection or deferral
- Updated baselines and communication plan

## 6. Stakeholder and responsibility map

| Work area | Accountable | Responsible / contributors | Consulted |
|---|---|---|---|
| Business process | Process owner | Business analyst, key users | Operations, quality |
| Solution architecture | Architecture owner | Solution architect, integration team | Information security, infrastructure |
| Delivery plan | Project Manager | Workstream leads, vendors | Sponsor, functional leads |
| Testing and acceptance | Business owner | Test lead, key users, vendor | Project Manager, IT operations |
| Go-live and support | Service owner | IT operations, vendor support | Business owner, Project Manager |

## How to use these examples

These templates are starting points. A real project should tailor them to its governance, delivery model, regulatory context, contractual obligations and decision rights. They should help teams make scope, ownership, risks, decisions and readiness visible — not create paperwork for its own sake.
